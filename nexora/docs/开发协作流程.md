# Git 开发协作流程（一页卡片）

> 适用：Nexora 项目多人合作。核心原则：**自己的活在自己分支上干，main 永远保持可发布状态。**

## 一、日常开发流程

```bash
# 1. 开始干活前：同步 main 到最新（必须先做！）
git checkout main
git pull

# 2. 从最新的 main 长出功能分支
git checkout -b feature/xxx        # 分支名：feature/功能名 或 fix/修复名

# 3. 开发 → 提交（小步提交，一次提交只干一件事）
git add .                            # 临时查看：git status
git commit -m "feat: 描述"

# 4. 推送远端并建立关联（只有第一次要 -u，之后直接 git push）
git push -u origin feature/xxx

# 5. 在 GitHub 上提 PR，review 通过后合入 main

# 6. 合入后：切回 main 同步，删除本地分支
git checkout main
git pull
git branch -d feature/xxx            # -d 会检查分支是否已合并，安全
```

## 二、分支关系图

```
本地                远端
main ────────────> origin/main
feature/xxx ─────> origin/feature/xxx   （origin/xxx 只是本地保存的远端快照，不能手动改）
```

## 三、同步命令速查

| 命令 | 作用 | 安全性 |
|---|---|---|
| `git fetch` | 只更新 origin/xxx 快照，不动工作区 | 绝对安全 |
| `git pull` | fetch + merge，把远端改动合进当前分支 | 可能有冲突 |
| `git push` | 把本地提交推上去 | 有冲突会被拒 |
| `git pull --rebase` | 线性化历史，团队约定使用则统一用 | 需先 stash 脏改动 |

冲突解决：git 标出 `<<<<<<<` `=======` `>>>>>>>`，手动改好后 `git add` + `git commit`（merge 冲突）或 `git rebase --continue`。

## 四、高频事故场景与对策

| 场景 | 正确操作 | 错误操作 |
|---|---|---|
| 想撤销上一次 commit | `git reset --soft HEAD~1` 或 `git commit --amend` | `git reset --hard`（真丢代码） |
| 想把工作区暂时收起来切分支 | `git stash` → 切过去 → `git stash pop` | 带着脏工作区直接 checkout |
| 改错分支了 / 在不该的位置 commit | `git log` 看 HEAD@{0}，`git reset --mixed <commit>` 后重新来 | 盲目 reset |
| 删了/弄丢了东西 | `git reflog` 找到之前的 commit，`git checkout <commit> -- <文件>` | 慌张继续操作 |
| 忘记分支和远端的同步状态 | `git status`（会提示 ahead/behind） | 凭感觉 |

## 五、保命三原则

1. **动命令前先 `git status` + `git log --oneline -5`** —— 确认自己在哪个分支、HEAD 在哪
2. **`--hard` 是最后手段** —— 它同时摧毁工作区+暂存区+指针，一律先用 `--soft` / `--mixed`
3. **`git reflog` 是后悔药** —— 任何 reset/checkout 都记录在案，顺着它一定能恢复

```bash
git log --oneline --graph --all   # 看全局：所有分支 + 远端 + 提交关系
```

## 六、本仓库的约定

- 开发从 `main` 拉分支，禁止直接往 main 提交工作内容
- 提交信息风格：`feat: xxx` / `fix: xxx` / `docs: xxx`（参考历史提交）
- 提交前检查：`git status` 无多余文件（注意 `nexora/resource/` 已 gitignore，上传的 PDF 不会被误提交）
