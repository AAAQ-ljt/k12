
### 整体流程梳理

```
上传PDF → 文档解析 → 文本分块 → 向量化 → 存入ES → 用户提问 → 意图分析 → 判断是否调用知识库 → RAG检索 → 拼接Prompt → 大模型生成回答
```

### 关于使用ES存储向量
Elasticsearch从8.0版本开始原生支持向量字段（`dense_vector`）和近似最近邻（ANN）检索，因此技术上完全可行。但更推荐的方案是**混合检索架构**：
* **ES（Elasticsearch）**：负责全文检索和元数据过滤（如按学科、学段、章节筛选）。
* **向量数据库（如Milvus/ChromaDB）**：专门负责语义相似度检索。
* **原因**：ES的向量检索能力相对基础，而专业向量数据库在大规模向量检索的性能和精度上更优。若追求开发效率，也可仅用ES同时承担两种检索功能。

### 以小学数学PDF为例的向量化入库流程
**① 文档解析**
使用PyMuPDF等工具提取PDF中的文本内容，同时保留页码、章节标题等结构化信息。

**② 文本分块**
将长文本切分为适合检索的小块。针对数学类材料，建议分块大小控制在**256~512个token**，相邻块之间保留**50~100个token的重叠**，避免公式或解题步骤被截断。

**③ 向量化**
调用Embedding模型将每个文本块转化为高维向量。推荐使用**通义千问的text-embedding-v3**（与赛题发榜单位中国移动/阿里生态契合），或开源的**BGE系列模型**（中文语义匹配表现优秀）。

**④ 存入ES**
每条记录包含以下字段：
| 字段 | 说明 |
|------|------|
| vector | 文本块的向量表示 |
| text | 原始文本内容 |
| subject | 学科（如"数学"） |
| grade | 学段（如"小学低年级"） |
| chapter | 章节（如"第三章-分数加减法"） |
| page | 页码 |
| source_file | 来源文件名 |

其中`subject`、`grade`、`chapter`等元数据字段非常关键，检索时可作为**前置过滤条件**，避免跨学段知识混淆。

### 用户端意图分析与RAG调用机制
**① 意图分析**
用户提问后，系统首先判断是否需要调用知识库。常见策略包括：
* **规则判断**：关键词命中特定学科/知识点时直接触发。
* **分类模型**：训练一个轻量分类器，将问题分为"需要检索知识库"和"通用对话"两类。
* **大模型判断**：直接在Prompt中让大模型判断是否需要检索（简单但增加延迟）。

**② RAG检索**
判断需要调用知识库后，执行以下流程：
```
用户问题 → 向量化 → 在ES中进行向量相似度检索（同时按学段过滤）→ 返回Top-K个最相关的文本块
```
**学段过滤至关重要**：小学低年级学生问"什么是加法"，绝不能检索到高中的微积分内容。检索时必须加上`grade`字段的过滤条件。

**③ 生成回答**
将检索到的文本块拼接到Prompt中，送入大模型生成最终回答：
```
你是一名小学数学老师，请根据以下参考资料回答学生的问题：

参考资料：
{检索到的文本块1}
{检索到的文本块2}
{检索到的文本块3}

学生问题：{用户原始问题}

要求：回答简洁易懂，适合小学低年级学生理解，不要编造参考资料中没有的内容。
```

### 技术选型建议（轻量方案）
| 环节 | 推荐方案 |
|------|---------|
| 文档解析 | PyMuPDF（PDF）、python-docx（Word） |
| 文本分块 | LangChain的RecursiveCharacterTextSplitter |
| Embedding | 通义千问text-embedding-v3 API |
| 向量存储 | ChromaDB（轻量原型）或 Milvus（生产级） |
| 全文检索+元数据过滤 | Elasticsearch |
| 编排框架 | LangChain |

如果追求最快出原型，可以全部用**LangChain + ChromaDB**搞定，几行代码就能跑通整个RAG流程。
